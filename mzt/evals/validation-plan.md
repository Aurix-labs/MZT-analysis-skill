# MZT 测试与验证方案

日期：2026-09-26

状态：已完成[第一轮开发集试跑](reports/2026-09-26-round-1.md)和[第二轮自动验证](reports/2026-09-26-round-2.md)。第二轮增加真实技能发现入口、前轮未运行的条件变体、原始材料和多轮纠错，共124个完整样本；本方案规定的逐方法全量验收、人工验收与真实任务效果验证仍未完成。

后续：已完成[调用与输出契约修复](reports/2026-09-26-invocation-repair.md)，最终版60次格式回归、10次复杂任务及1次五轮模式回归通过，并同步已安装副本。本轮未启动N/G/M增益实验，不能据此改变“尚未证明方法论有额外收益”的结论。

适用范围：MZT 运行入口、23 篇方法参考，以及它们在指定模型和宿主中的实际使用效果。

## 1. 验证目标与基本原则

本方案需要分别回答四个问题：

| 问题 | 所需证据 | 不能替代它的证据 |
|---|---|---|
| 是否正确加载 | 实际运行文件的版本、哈希、加载记录和宿主设置 | 仓库中存在 SKILL.md；agent 自称已使用 |
| 是否正确运用 | 可见答复、工具动作、产物、证据使用及多轮修正 | 方法名称、固定标题、理论引文、文风相似 |
| 是否带来增益 | 相同运行条件下，有技能与无技能的配对比较 | 单个好答案；只比较两个不同模型 |
| 是否在实际任务中有效 | 建议、执行、现实结果与后续修正的记录 | 用户满意；方案自洽；模型自评通过 |

MZT 是思考指导。评测检查它是否改善对事实、关系、条件和行动的判断，不要求 agent 展示固定步骤或在每题使用全部方法。覆盖表约束出题与验收，不成为运行时的回答模板。

只评价可见理由、公开答复、实际工具动作和成果，不索取、存储或评分隐藏思维链。允许不同但有充分依据的结论；方法不适用时，直接完成任务同样可以通过。

## 3. 测试单位、题库规模与数据划分

统一以下计数，避免用运行次数放大题库规模：

- **场景家族**：共享同一现实机制或基础材料的一组任务。
- **用例**：可独立判分的任务及其轮次协议；一个多轮用例包含完整对话，不按轮次重复计题。
- **变体**：同一家族中改变关键条件或无关表述形成的另一用例。
- **运行样本**：一个用例在一个组别、一次独立重复中的实际输出。
- **运行条件**：显式调用、自然触发、模型、宿主等。删除 `/mzt` 本身不增加方法覆盖。

首版规模按两步推进：

1. 保留现有 17 题，规划约 13 个新增基础场景，使基础场景达到约 30 个。
2. 围绕关键条件、误用边界和多轮反馈扩为约 50—70 条用例。

这是工作量估计，不是统计充分性的证明。最终数量由覆盖缺口和实际失败决定。已有题之间若共享同一机制，应归为同一家族，不能假定 30 个题目一定等于 30 个独立家族。

按家族预先划分开发集与保留集，目标约 80% / 20%。同一家族的基础题、改写、变体和多轮版本必须在同一集合。现有公开题、技能示例及其近似改写不能冒充未知保留题。

保留题使用未参与 skill 调整的独立材料，覆盖多个领域与难度，不能全是更难或更容易的题。仅在候选版本冻结后验收；一旦据其反馈修改 skill，该家族即转入开发集，并补充新的保留题。本方案公开的场景方向不是密封保留题，具体材料仍需另行制作和管理。

## 4. 方法覆盖标准

每种方法至少建立三类有明确判据的设计覆盖：

| 类型 | 需要区分的行为 |
|---|---|
| A：适用 | 能利用相关关系或机制改善具体判断与行动 |
| B：边界 | 面对典型误用诱因，能限制、放弃或调整该视角 |
| C：条件变化 | 决定性条件变化后更新受影响的判断；无关变化不引起无依据翻转 |

每个覆盖单元必须有：方法编号、行为断言、对应材料、可能的错误行为、可见判分证据、用例 ID、状态。状态区分“已设计、已运行、通过、失败、未测量”。

一题可覆盖多个方法，但每个映射都要有独立、可核对的行为依据。仅出现术语、读取文件或贴标签不计覆盖。设计覆盖完成也不等于能力已通过。

## 5. 新增基础场景设计

P18—P30 已在第一轮独立题库快照中具象化为条件变体，原 evals.json 仍保留17题。以下保留设计方向；实际用例、开发集与暂存保留集划分见[第一轮报告](reports/2026-09-26-round-1.md)。出题时应提供能支持判断的具体材料、时间顺序和现实约束，避免只写一个宽泛讨论题。

第二轮已使用上述暂存保留集中的12条条件变体，并新增H01—H04四个原始材料场景；运行包保持冻结。后续若依据这些结果调整skill，应将相关家族转入开发集，并另建独立保留材料。两轮累计实际运行57个不同用例；样本重复数、场景家族数与逐方法覆盖不能相互替代。

| 编号 | 基础场景 | 关键变体或后续材料 | 主要验收行为 |
|---|---|---|---|
| P18 | 小团队投入半年、现金有限，续费与交付能力出现改善 | 保持投入历史相同，改变改善是否依赖补贴、竞争者追赶速度和现金消耗 | 判断时间与积累是否有利，依据条件选择继续、缩小、调整或停止 |
| P19 | 客服处理时长下降，但重复求助上升 | 另一版本中解决率也持续改善，并控制样本口径 | 区分真实改善与成本转移，不因 KPI 存在就全盘否定 |
| P20 | 合作渠道帮助交付，但包含独家限制与数据迁移障碍 | 改变退出条件、可验证替代方案及自建成本 | 比较合作收益、约束、选择权和能力建设，不预设全自建或全外包 |
| P21 | 维修团队被批评不上报缺陷，但先前上报者受到处罚 | 移除惩罚条件，并提供实际可用的上报渠道和责任记录 | 同时检查制度、管理责任和个人行为，提出能作用于原因的处理 |
| P22 | 学校或服务网点的试点明显提效，但有额外人员驻场 | 后续显示普通条件下的复现结果，或显示效果无法复现 | 核查机制、测量与推广条件，利用一线反馈调整方案 |
| P23 | 公共服务调查中多数人支持便利措施，少数人承担明显不便 | 提供不同群体的参与率、严重负担及替代安排 | 检查代表性、实际处境和实施反馈，既不简单多数决，也不虚构代表意见 |
| P24 | 工厂将资源集中于一道工序，其局部产出上升而整体交付不变 | 提供下游容量、维护需求及不同资源分配后的可比结果 | 查明瓶颈及转移成本，区分真正突破与局部指标优化 |
| P25 | 同一合作项目发生激烈争执 | 分别给出信息误解、资源硬冲突、持续违约三种机制 | 处理方式随关系性质变化，不一律劝和，也不因语气激烈就判定敌对 |
| P26 | 外部供应冲击影响多个条件不同的经营主体 | 同样冲击下改变库存、议价权、替代渠道和可控行动 | 解释外因如何通过内部条件起作用，既不忽略外部冲击，也不无限归责个人 |
| P27 | 多个瓶颈并存，一方拥有最终决定权 | 改变决定性约束，保持权力归属不变；再做相反变体 | 区分全局关键关系、关系中的主导方面和方案是否合理 |
| P28 | 应急资源有限，需要决定集中处理还是多组并行 | 改变任务依赖、专业能力和安全保障条件 | 调整手段而保留任务目标，不机械串行，也不以长期信心省略具体准备 |
| P29 | 跨部门反复不共享资料，最初被解释为态度问题 | 依次出现权限日志、激励记录、解除限制后的行为反馈 | 用调查区分竞争解释，并修正自己先前的定性 |
| P30 | 修改办事入口后首次使用增加，但持续使用没有变化 | 明确先前假设只关于可发现性，或同时声称能改善持续使用 | 只修正被结果反驳的部分，不以局部成功宣布全部有效，也不以局部失败推翻全部解释 |

这些是出题方向，不是标准结论。每题应记录允许成立的不同结论及其证据条件，避免把作者偏好写成正确答案。

## 6. 用例结构与专项测试

每个用例至少准备两份相互隔离的材料：

| 作答包 | 评审包 |
|---|---|
| 自然任务、当前轮允许读取的材料、工具与权限、用户明确限制 | 家族与方法映射、事实依据、必须满足的行为、严重错误、允许的结论范围、变体关系、判分方式 |

运行元数据另存组别、版本、重复编号和盲评映射，不向作答者暴露评审包。

用例定义保留现有 prompt、files、follow_up_prompts、follow_up_files、objective_constraints 字段。执行阶段再以独立 sidecar 增加 family_id、variant_id、集合归属、方法行为映射和判据；无需为整理方案先改动现有题库 schema。

必须包含以下专项：

- **关键条件敏感性**：例如互换评审等待与测试环境等待，观察干预点是否随证据变化。主要改变一项决定性因素；组合变化须单独标明，不能据此归因于单个因素。
- **无关变化稳定性**：只改姓名、材料顺序、用户情绪或偏好，比较实质判断是否无依据翻转。若身份影响权限、资源或利益，它就不是无关变量。措辞不同不算失败。
- **真实多轮修正**：包括新事实、测量纠正、当事人改口与用户无依据施压。应随有效证据修改，同时拒绝无依据改口。只在题面复述一个旧答案，不算真实续轮。
- **证据不足和工具异常**：材料缺失、来源互相冲突、工具不可用。检查能否限定结论、利用已有证据继续合理工作，而非编造核验结果。区分宿主缺陷与 agent 的应对质量。
- **适用边界与基本任务**：保留算术、代码、翻译、指定格式、既定方向等题。简单任务不需要显示方法分析；复杂任务也不能为了短而省略必要论证。
- **自然触发与模式语义**：在新会话中不写 `/mzt`，检查宿主能否按其发现机制选择并加载技能。显式 on/off 单独验收，只检验可观察的命令响应与后续行为，不推断内部状态或跨会话持久化。

自然触发应独立于“已加载后的能力”报告。若宿主不支持自动发现，该项记为能力未提供，不把 agent 答得好当成触发成功，也不把宿主限制混入方法运用失败。普通任务中是否加载的期待应依据宿主发现策略预先定义，答复是否被无关分析干扰则始终可检查。

## 7. 对照组与运行环境

主实验设置：

| 组别 | 内容 | 用途 |
|---|---|---|
| C：当前技能 | 冻结的当前运行包，允许按需读取其参考文件 | 检查当前行为和质量 |
| N：无技能 | 相同模型、工具、任务与材料，未发现、加载或继承 MZT | 判断技能的增量效果 |
| O：冻结旧版 | 在版本变更验收时增加可追溯的旧版运行包 | 检查改动收益和退步 |

初次基线至少使用 C/N；O 组在可用时加入。第 13 题的模式命令不与无该语义的 N 组硬比较。自然触发只给 C 组相应发现入口；能力对照则确保 C 已加载指定版本。两类实验的结论分开报告。

每次运行冻结并记录：

- 实际模型标识、可用推理强度、采样参数、上下文与输出限制；未知字段如实标记。
- 宿主版本、系统与项目指令、其他可用技能、工具集合、权限和时间限制。
- 技能入口、可供读取的参考文件、题库、评分规则及输入材料的内容哈希；有未提交改动时保存实际快照。
- 实际安装目录与仓库的关系，不能用仓库版本替代加载版本。源文件与安装副本分别核对。

对照隔离要求：

1. 每个用例和每次重复使用新会话，多轮用例仅在本次运行内续接。
2. N 组清除 MZT 的发现条目、正文、参考文件注入、相关记忆及先前对话。仅移除命令前缀不够。
3. C 组只获得运行所需的技能包，不复制 evals、历史答案、评分文件或未来轮次材料。
4. 使用临时目录或宿主可提供的沙箱，避免运行环境访问评审包。若只能依靠指令隔离，记录限制并审计可见访问轨迹；不得宣称严格隔离。
5. 各组采用同一澄清规则和可用信息。agent 询问时按预先准备的事实库答复，不临时给某组更多提示。
6. 使用冻结虚构材料的主测试，和需要真实检索的补充测试分开。前者无需上网寻找虚构对象；后者统一检索能力，记录来源时间和内容，动态变化列入局限。
7. 打乱组别运行顺序，避免时间漂移总影响同一组。跨模型或跨宿主时重新配对，不能将差异直接归因于 skill。

若运行器不能证明无技能组未受污染，就只能报告环境受限的探索结果，不能作严格的因果增益声明。

## 8. 执行顺序与重复安排

| 阶段 | 操作 | 交付与退出条件 |
|---|---|---|
| A：静态准备 | 核对运行包、引用、题库、评分脚本契约、文件供给和隔离能力 | 材料有效；版本可追溯；已知环境限制记录完整 |
| B：出题与评审校准 | 建覆盖表、补题、划分集合；用专门的校准样本检验判据 | A/B/C 设计覆盖无空白；明显错误和合理异答能被正确区分 |
| C：开发集试跑 | 先按现有 17 题 C/N 各运行一次，再加入新增开发题；模式题按适用组运行 | 核对实际加载、供给、轨迹、产物和判分；定位失败，不宣称整体稳定 |
| D：失败定位与修订 | 对失败、差异明显、不稳定题每组独立重复至少 5 次；必要时修改技能 | 保留全部样本；每次修改另建版本；重跑相关家族及基础回归 |
| E：冻结候选版本 | 停止据保留集调优，固定用例、组别、重复数、指标和验收规则 | 运行清单可以复现；确认成本后按已授权范围执行 |
| F：正式验收 | 声称全套稳定性或整体增益时，对完整适用测试集采用相同重复安排，首版每组每例至少 5 次；包含保留集 | 输出逐题及逐家族结果、差异与不确定性；不能只重复有利题 |
| G：实际任务反馈 | 在正常获授权的真实任务中记录建议、实际执行和观察结果 | 分清沟通体验、行为质量与现实效果，持续积累新的失败家族 |

重复数用于观察波动，不自动提供统计保证。若完整验收超过预算，缩小本轮结论范围并列出未测项；不能把部分运行写成完整通过。未经授权不自动启动持续监控、外部操作或现实试验。

粗略成本按“适用用例数 × 组别数 × 重复数”估算完整运行样本；多轮调用与评审另计。例如 60 条全部适用用例、2 组、5 次约为 600 个完整样本，不是 600 条单轮消息。应先用试跑测量每家族成本，再确定正式规模。

## 9. 评分方法与评审校准

继续使用 [rubric.md](rubric.md) 的五个维度：事实与证据、目标与约束、主次与因果、可修正性、表达与任务适配。保留现有 1/3/5 锚点和 N/A 规则，不新造一个靠术语计数的综合分。

每个样本同时记录：

- 结果状态：成功、失败、无效、未测量。
- 逐条关键行为是否满足，以及对应原文、工具动作或产物位置。
- 适用维度的评分、理由和最重要缺陷。
- 严重错误类别；实际时长、调用量与 token 仅使用运行器提供的数据。

成功要求完成用户任务、满足该题预先定义的关键行为和明确限制，且无严重错误。单靠维度均分不能决定通过。有限材料下正确保留结论可以成功；要求调查的题仅给调查计划则不能成功。

严重错误至少包括：虚构关键事实或来源、未核验却声称已核验、误读决定性政策对象、无视关键反证、用身份或传闻认定动机、违背明确任务边界、错误程序行为、把未发生的执行或效果写成已完成。按具体任务确认严重程度，不把轻微表达问题一律升级。

判分分工：

| 方式 | 适合检查 | 限制 |
|---|---|---|
| 程序 | 显式长度、确定计算、代码行为、文件供给与可核验状态 | 现有 check_objective.py 仅支持字符和行数限制；其他检查需单独实现 |
| 独立模型评审 | 证据是否支持判断、条件是否影响行动、修正是否恰当 | 隐藏组别和方法标签，不看作者自评；结论必须附可见证据 |
| 人工复核 | 严重失败、模型评审分歧、来源与核心概念、随机抽样 | 最终报告标明哪些样本经过人工复核；未做则不得标称已人工验收 |

正式评审前制作约 8—12 份独立校准答复，包含：合理异答、短而正确、长而空泛、有真实利益证据但不推断动机、语气自信但关键事实错误、只承认新信息却未调整建议。校准样本不进入能力统计。

评审须能够识别预设的严重错误，接受证据支持的不同结论；关键分歧经人工裁定后再运行正式评分。若修改判据，对受影响的全部样本重新评分并保留旧评分，不只修正某一组。

匿名配对比较时随机排列左右答案；评审只取得任务、允许材料、输出与可见动作。抽查交换左右顺序是否影响结果。预先固定长度偏好边界，不能奖励篇幅本身。记录评审模型与生成模型是否相同。

## 10. 指标、有效性与结论边界

必须报告的指标：

| 指标 | 口径 |
|---|---|
| 设计覆盖 | 23 种方法的 A/B/C 单元是否存在有判据的用例；与运行通过率分开 |
| 任务成功率 | 成功样本 / 有效运行样本；同时报告原始数量和未完成项 |
| 严重错误率 | 含严重错误的有效样本比例，并列出类别与具体案例 |
| 重复稳定性 | 每用例 k/n 成功分布，例如 4/5；不能以至少一次成功代替可靠性 |
| 条件敏感性 | 预定义成对判据通过数 / 有效条件变化配对数 |
| 无关变化稳定性 | 无关变体间没有无依据实质翻转的配对比例 |
| 多轮修正 | 更新受影响判断且保留有效部分的完整对话比例 |
| 对照差异 | C/N、必要时 C/O 的成功率差及盲评胜/平/负，按家族展示 |
| 任务适配 | 简单任务、格式、代码、既定方向等基础回归的成功情况 |
| 运行成本 | 实测耗时、工具调用、token；缺失时标未测量 |

同时报告有效样本覆盖率。评分泄露、组别串包、错发材料、非 agent 导致的环境崩溃记为无效或未测量，并保留原因；agent 在正常权限内作出错误读取或操作则按行为判定，不一律归咎环境。超时和输出截断的归类按预先冻结的预算及原因处理，各组规则一致，不能把失败样本随意剔除。

按场景家族汇总，避免一个家族增加很多变体后支配总结果。家族内重复与变体相关，不能全部当成独立题。置信区间应采用尊重家族结构的配对分析，例如按家族聚类重采样；样本不足时以分布和案例报告，不制造精确感。

若要声称“整体改善”，在正式运行前指定主指标，默认是家族等权的配对任务成功率差，同时检查严重错误和基础回归。支持正向差异的区间证据及保留集同向结果才能支持所测范围内的改善判断；区间跨零则记为证据不足。若拟以盲评质量作为主指标，须提前指定，不能看到成功率没有提升后才改选有利指标。

一次回答中体现多个方法，不能据此证明每种方法各自造成了收益。需要验证某篇参考文件的独立贡献时，再开展完整技能与移除该参考内容的受控比较；首轮不必穷举所有组合。

## 11. 首版验收规则

这些是本方案提出的工程验收规则，不是已经取得的结果。正式运行前将适用集合与规则冻结，修改规则必须记录原因和新版本。

| 层次 | 通过条件 | 可作出的结论 |
|---|---|---|
| 评测设计就绪 | 23 种方法均有 A/B/C 设计映射；基础任务、组合场景、自然触发、多轮和保留集都有明确口径 | 题库可以检查已识别的核心行为与边界 |
| 运行有效 | 输入、版本、加载、访问、供给和评分可追溯；未测及无效项明确；无泄露的样本才进入主结果 | 本批样本可用于相应范围的判断 |
| 候选版本达到行为门槛 | 预先指定的关键回归集合在正式重复中全部通过；整个验收批次未观察到严重错误；其他失败逐项解释，不得把未测记通过 | 在指定环境和已测集合上达到约定门槛 |
| 增益得到支持 | 同条件配对、足够重复、保留集以及预先指定主指标支持改善，且无新增严重错误或关键回归退步 | 在所测模型、宿主、任务范围内有改善证据 |
| 实际效果得到支持 | 有真实执行与结果，并检查其他可能解释 | 对具体行动效果有相应强度的证据 |

关键回归集合应包含：明确格式与任务边界、事实和来源不编造、必要调查、利益证据边界、关键反证修正，以及每种方法最容易造成实质错误的误用用例。具体用例清单在运行前冻结，不能事后挑选全部通过的题组成集合。

五次全部通过只表示本次观察为 5/5，不代表未来失败概率为零。C/N 表现相近时，可以报告当前版本可用且未见明显退步，但不能宣称 skill 带来了提升。尚未人工复核时单独标记“自动评测完成，人工验收未完成”。

## 12. 故障定位与维护

失败先归入证据链中的位置，再决定改哪里：

| 失败位置 | 优先检查 |
|---|---|
| 未发现或加载错误版本 | 描述、安装目录、宿主发现机制、缓存和运行包 |
| 加载后未读取必要材料 | 任务与工具可见性、调查要求、权限和工具返回 |
| 读取后误解或无依据推断 | 概念边界、示例暗示、事实断言和推断条件 |
| 新信息未影响建议 | 修正要求是否具体，agent 是否维护了错误前提 |
| 简单任务被方法分析干扰 | 入口与参考材料是否把思考要求写成输出要求 |
| 正确答案被判失败 | 判据是否过窄、评审是否偏好固定结论或文风 |
| 环境出错 | 运行器、文件供给、权限、超时和隔离实现 |

修改应对应可复现的问题，不因单次失误无限扩写 skill。每次修改保留失败样本、内容差异和新版本，重跑相关家族及关键回归。模型升级、宿主变化、安装同步或新增参考文件，也应触发相应回归，不直接沿用旧验收结论。

## 13. 记录、文件与交付

首先使用现有 JSON、Markdown、文件快照和简洁运行记录，不以建设评测平台作为开始验证的前提。需要反复运行后，再实现最小运行器。

拟议文件职责：

| 路径 | 用途 | 当前状态 |
|---|---|---|
| `mzt/evals/validation-plan.md` | 完整方案与验收规则 | 本次新增 |
| `mzt/evals/evals.json` | 现有开发题与后续新增题 | 本次未修改 |
| `mzt/evals/rubric.md` | 共用评分维度和行为准则 | 本次未修改 |
| `mzt/evals/coverage.json` | 方法—行为—用例映射与设计覆盖状态 | 拟新增 |
| `mzt/evals/case-metadata.json` | 家族、变体、判据和集合归属 | 拟新增，仅评审侧读取 |
| `mzt/evals/fixtures/` | 可分轮供给的开发材料 | 现有材料保留，拟扩充 |
| 独立评审目录中的保留题 | 未参与调优的具体任务与依据 | 拟新增，不放进作答包 |
| `docs/reviews/<run-id>/` | 运行清单、快照、样本、评分和报告 | 每轮单独生成；该目录当前被 Git 忽略，归档方式需显式记录 |

每个运行至少保存：run_id、case_id、family_id、variant_id、split、arm、repeat_id、环境与文件哈希、当轮输入、完整可见答复、可见工具动作及结果、产物、机械检查、逐条判据、评分证据、有效性、严重错误和实测成本。盲评标签映射单独保存。

不保存隐藏思维链或无关凭证、个人信息。保留集、评分文件和运行结果不得混入发布的 skill 运行包。

报告按照以下内容交付：

1. 本次版本、环境、范围、未测项与结果结论。
2. 方法设计覆盖、运行覆盖和主要缺口。
3. 逐题与逐家族成功、失败、重复波动及严重错误。
4. C/N 与必要时 C/O 的配对差异、保留集结果及不确定性。
5. 典型改善、持平、退步案例，附具体证据。
6. 实测成本、环境局限、人工复核范围。
7. 修改建议、回归清单，以及允许作出和不能作出的能力声明。

## 15. 依据

本方案沿用当前 [MZT 行为评测 v2](rubric.md) 的行为证据、对照、盲评、重复与隔离要求，并将此前讨论的题库扩充和方法边界覆盖具体化。

程序检查、模型评审与人工复核的分工，以及同时检查实际结果和运行记录的原则，可参考 [Anthropic：Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)。本文的题量、阶段安排和工程验收规则为本项目方案，不是该文章提供的统一行业阈值。
